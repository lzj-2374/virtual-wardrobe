# 虚拟衣柜 · AI 穿搭推荐系统

以用户**真实衣柜**为数据源的穿搭助手：上传衣物后自动识别属性，再基于你自己的衣服生成搭配方案，并渲染模特上身效果图。

不同于「随机换装」类玩具，这个项目的所有推荐都只能从用户已录入的衣物里挑——AI 负责搭得好看，后端负责保证搭得对。

---

## 功能

| 模块 | 说明 |
| --- | --- |
| 衣物管理 | 上传图片，视觉模型自动识别品类、颜色、季节、厚薄并打上场合标签 |
| AI 对话推荐 | 自然语言提问（"明天 15 度上班穿什么"），解析意图后生成 1~3 套搭配 |
| 上身效果图 | 以真实单品图作底图做图生图，输出模特穿着效果，异步生成不阻塞请求 |
| 我的搭配 | 手动创建 / 从 AI 推荐一键保存，支持封面与详情 |
| 数据统计 | 衣柜构成、颜色分布、场景偏好 |
| 管理端 | 用户管理、数据导出、仪表盘 |

## 快速开始

### 1. 前置依赖

- JDK 17、Maven 3.8+
- MySQL 8（库名 `virtual_wardrobe`，字符集 `utf8mb4`）
- Redis 7（默认用 `db 1`）
- RabbitMQ 3（管理台 15672）
- Node.js 18+

### 2. 初始化数据库（顺序不能反）

```bash
# 建库
CREATE DATABASE virtual_wardrobe DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_general_ci;

# 第一步：7 张基础表 + 品类字典
mysql -uroot -p virtual_wardrobe < db/init.sql

# 第二步：5 张 AI 表（依赖上面的表）
mysql -uroot -p virtual_wardrobe < backend-full/sql/schema-ai.sql
```

一共 12 张表。`schema-ai.sql` 只新增 AI 相关表，不修改已有结构。

### 3. 启动后端

```bash
cd backend-full
mvn spring-boot:run
```

服务地址 `http://localhost:8080/api`（注意有 `/api` 前缀）。

### 4. 启动前端

```bash
cd frontend
npm install
npm run dev
```

访问 `http://localhost:5173`。Vite 已把 `/api` 代理到 `localhost:8080`，无需额外配置。

## 密钥配置（可选）

API Key 和数据库密码放在 `backend-full/config/secrets.yml`，该目录已被 `.gitignore` 排除。

新建这个文件：

```yaml
aliyun:
  oss:
    access-key-id: LTAI****************
    access-key-secret: ****************************

ai:
  llm:
    api-key: sk-****************     # DeepSeek
  image:
    api-key: sk-****************     # DashScope，生图与衣物识别共用
```

**不配也能跑。** 缺少密钥时系统自动降级：

| 缺什么 | 降级后果 |
| --- | --- |
| `ai.llm.api-key` | 不走大模型，改用内置规则引擎（按季节 / 厚薄 / 场景标签打分组合） |
| `ai.image.api-key` | 不走万相，改用服务端合成（拿真实单品图拼一张平铺图） |
| `aliyun.oss` | 图片落本地磁盘，接口返回相对路径 |

降级后功能语义不变，只是「聪明程度」下降——这样 clone 下来不用申请任何 key 就能看到完整流程。

## 关键设计

### AI 推荐：双通道 + 返回后校验

大模型负责「搭得好看」，规则引擎负责「搭得对」。

```
用户提问
   ↓
意图解析（场景 / 季节 / 气温 / 风格，支持从上一轮继承）
   ↓
┌─────────────┐   失败自动降级   ┌──────────────┐
│ DeepSeek    │ ───────────────→ │ 规则引擎      │
│ 提示词 + JSON│                  │ 打分 + 组合   │
└─────────────┘                  └──────────────┘
   ↓
五道校验：衣物 id 真实存在 / 同套内品类不重复 / 必须有上装
          / 季节自洽 / 用户指定的单品必须用上
   ↓
全部不通过 → 整套丢弃 → 降级到规则引擎
```

规则引擎的分值维度：季节匹配、厚薄匹配、场合标签命中、中性色偏好。

### 生图：异步队列

图生图单张耗时 60 秒上下，不能放在 HTTP 线程里。

```
POST /ai/image/generate  →  落任务记录 + 投递 MQ  →  立即返回 taskId（~80ms）
                                    ↓
                          RabbitMQ → 消费者 → 调万相 → 转存 OSS → 回写状态
                                    ↓
前端每 1.5s 轮询 GET /ai/image/status/{taskId}（退避至 10s）
```

可靠性做了四层：

- **生产端确认**：`ConfirmCallback` 发现消息没到交换机，`ReturnsCallback` 兜住"交换机找不到队列"，两者都会把任务回写为失败，避免永远卡在「生成中」
- **消费端重试**：3 次本地重试，间隔递增
- **死信兜底**：重试耗尽进 `wardrobe.ai.image.dead`，不会无限重放刷额度
- **幂等**：消费前查状态 + `WHERE status <> 2` 条件更新，重复投递不会重复调 API、重复扣费

### 季节过滤：位掩码 + 硬过滤

季节用位标识存储（春 1 / 夏 2 / 秋 4 / 冬 8 / 四季 15），判断必须用位与而非相等。

候选池按位与做**硬过滤**——穿不了的单品直接出局，而不是扣分。原因是衣柜小的时候扣分拦不住：只有一条夏装短裤时，它扣完分仍然是唯一选项。用户指定单品时，以该单品的季节为准，覆盖从上下文继承的气温。

### Prompt 体积控制

单次推荐请求稳定在 **3000 token 以内**：system 提示词约 430 + 衣柜清单上限 50 件约 1340 + 最近 3 轮上文约 90 ≈ 1800 输入，输出上限 1200。

衣柜超过 50 件时按「用户指定的 → 当季能穿的 → 其余」截断，避免输入随衣柜规模线性膨胀。

## 已知限制

- **图生图单张约 60 秒**，前端轮询最长等 4 分钟；超时后按钮变为「再查一次」，不会重复生成
- **没有做 RAG**。这个场景的候选集就是用户自己的几十件衣服，全量塞进提示词完全放得下，而且穿搭的核心约束是品类互补而非语义相似，向量召回反而会召回一堆同款 T 恤
- **轮询而非长连接**。分钟级任务用轮询的复杂度远低于 WebSocket，且刷新页面后能靠 taskId 接着查——这是长连接做不到的。当前间隔有退避，一次生图约 8 次请求
- **图片存储强依赖公网地址**。图生图需要把底图上传到可公网访问的 OSS，本地磁盘模式无法启用 AI 出图
